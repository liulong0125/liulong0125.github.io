一个广泛使用的 ``javascript`` 编译器。能把新版本的 ``javascript`` 代码( ``ES6+`` )转换成旧版本（ES5）代码，让代码在老旧的浏览器环境中正常运行。

## 前言

+  ``javascript`` 特性分类
  + 稳定特性: 所有已经正式定稿的 ``ECMAScript`` 标准 ``API`` 。
  + 实验性提案: 所有处于 ``Stage 0`` 到 ``Stage 4`` 阶段的特性（ ``Proposals`` )。
    + ``Stage 0`` - ``Strawman`` （展示阶段/稻草人）: 这只是一个自由倡议，任何 ``TC39`` 会员都可以提出。它代表一个构想或初步想法，随时可能被推翻、重写、或者被完全遗弃。
    + ``Stage 1`` - ``Proposal`` （征求意见阶段/提案）: 该构想得到了 ``TC39`` 委员会的正式关注，认为它值得继续深入讨论，此时需要产生正式的公开文档，描述该语法要解决的问题，具体的解决案例以及详尽的 ``API`` 样式。
    + ``Stage 2`` - ``Draft`` （草案阶段）: 这一阶段的语法已经非常明确，开始编写规范的初稿（ ``Draft`` ）。在这个阶段，语法的核心细节基本敲定，原则上不应该再做重大修改，只进行细节微调。
    + ``Stage 3`` - ``Candidate`` （候选阶段）: 规范文本已经完成全冻结，不再接受任何来自 ``TC39`` 内部的修改。这个阶段的唯一目的，是等待外部生态（如各大浏览器引擎、Babel社区、TypeScript 社区）对其进行实际落地测试并反馈 ``bug`` 。
    + ``Stage 4`` - ``Finished`` （完成阶段/正式标准）: 提案已经具备成为标准的所有条件，它将正式写入下一年度发布的 ``ECMAScript`` 官方大版本规范中。
  + ``Web`` 标准分类: 一些非 ``ECMAScript`` 但常用的 ``Web`` 浏览器 ``API`` （e.g. ``URL.URLSearchParams`` 等）。
    + ``core-js`` 对 ``web`` 标准是选择性支持，并非全盘接纳。
    + 常见的拒绝场景
      + 严重依赖 “输入输出设备、硬件、DOM渲染” 的 ``Web API`` 
        + 被拒绝的代表: ``Canvas API`` 、 ``Web Audio API`` 、 ``IntersectionObserver`` （监听元素可见性）、 ``LocalStorage/IndexedDB`` （存储）。
        + 原因: ``core-js`` 运行在纯 ``js`` 引擎层。旧浏览器如果不支持 ``Canvas`` ，说明她底层没有绘图引擎。 ``core-js`` 作为一段 ``js`` 代码，不可能凭空在屏幕上画出像素，也不可能凭空生出一个硬盘存储区。
      + 严重依赖 “系统网络堆栈” 的 ``Web API``
        + 被拒绝的代表: ``fetch`` 、 ``WebSocket`` 、 ``XMLHttpRequest`` 。
        + 原因: 这些 ``API`` 涉及网络协议（ ``HTTP/3``、 ``TCP`` 、保持长连接等）。作为基础标准库， ``core-js`` 拒绝吧一个庞大的网络请求库（e.g. ``whatwg-fetch`` ）打包进自己的核心。
      + 由于 ``js`` 语言限制，技术上根本无法实现（不可逆）的特性
        + 被拒绝的代表: ``WeakRef`` （弱引用）、 ``Proxy`` （代理）。
        + 原因: 虽然它们都属于 ``ECMAScript`` 规范，但它们需要垃圾回收机制（ ``GC`` ）的底层配合。在不支持的旧引擎里，纯 ``js`` 绝对无法再运行时伪造出 “弱引用” 或 “拦截对象属性读取” 的行为。

+ 浏览器端运行 ``js`` 的 3 个核心拆解
  + ``ECMAScript``: 核心语法标准， ``ECMA`` 组织制定。
  + ``DOM`` 规范: 文档对象模型， ``W3C`` 组织制定。
  + ``BOM`` 规范: 浏览器对象模型， ``WHATWG`` 组织制定。




## 发展历程

+ ``6.x`` 时代（2014~2015）: 原名 ``6to5`` ，早起专注于 ``es6`` 转换 ``es5`` , ``6.0`` 版本重构为插件化架构并改名为 ``Babel`` （意为巴别塔）。
  + 插件化架构: ``6.0`` 之前是功能全包（开箱机用），插件化后所有转换的插件都是单独安装包，自己（ ``babel-core`` ）不负责任何逻辑，只进行读（解析 ``Parse`` 代码并生成 ``AST`` 抽象语法树）写（访问代码节点树进行广播让安装的插件进行转换后并输出，替换原有的 ``js`` 代码）。
+ ``7.x`` 稳定期（2018至今）: 迁移至单仓库管理，调整了包命名规则（废弃 ``babel-preset-es2015`` 等，改名 ``@babel/preset-env`` ），全面拥抱模块化和现代前端工程体系。
  + 为什么迁移至单仓库管理（Monorepo - Monolithic Repository，babel 的 git 仓，重构后的仓为 ``/babel/babel`` 其它仓全部整合到了 ``pacakges`` 目录下 ）？
    + 多仓的痛点: 核心功能（ ``babel-core`` )、各个插件（ ``babel‑plugin‑transform‑arrow‑functions`` 等）、各个预设（ ``babel-preset-es2015`` 等）都是各自独立的代码仓库。
      + 提 ``issue`` 找不到地方。
      + 版本碎片化，各走个的安装时以及发生冲突。
      + 联动修改机器麻烦，如果 ``Babel`` 团队要在核心包里加一个新特性，这个特性需要修改 5 个插件。开发者必须克隆 5 个仓库，分别修改提 ``PR`` 、分别发布到 ``npm`` 。
    + 单仓后，团队实行了 “全家桶整齐划一” 的策略。
      + 不管发布多么微小的更新， ``@babel/core`` 、 ``@babel/preset-env`` 等所有官方包的版本号强行同步。
      + 统一之后的好处就是所有包都是同步版本， ``peerDependencies`` 放心的声明 ``{ @babel/core": "^7.22.5" }``，因为大家版本都是一样的，之前版本号差异巨大，很难准确描述对等依赖版本。
  + 既然重构为了单仓，为什么 ``babel-polyfills`` 、 ``babel-loader`` 、 ``babel-eslint`` 这几个包还是独立仓？
    + ``babel-loader`` : 该包属于 ``webpack`` 组织，而不是 ``Babel`` 组织（如果没有 ``babel-loader`` ， ``webpack`` 和 ``babel`` 就是两个独立的工具）。
      + 生态归属权: ``babel-loader`` 是 ``webpack`` 的一个插件，用来连接 ``webpack`` 和 ``babel`` 。在 ``github`` ，它的官方仓库是 ``webpack/babel-loader`` ，版权和维护者主要属于 ``webpack`` 团队。
      + 职责分离（解耦）: ``babel`` 团队只专注于构建核心编译器（ ``Parser`` 、 ``Transformer`` 、 ``Generator`` ）。至于代码时如何被打包工具（e.g. ``webpack`` 、 ``vite`` 、 ``Rollup`` ）加载的，应该由各个打包工具的生态去自行维护。
      + 避免绑定: 如果把 ``babel-loader`` 放进 ``babel`` 仓库，不仅 ``webpack`` 团队不方便维护，也会让外界误以为 ``babel`` 只能和 webapck 强绑定。
    + ``babel-eslint`` : 它已经被废弃了，但它的 “转世” 其实就在 babel 主仓里面。
      + 历史背景: babel-eslint（现在叫 @babel/eslint-parser ，在 babel 的 7.7.0 开始已经纳入了 babel 的单仓中）以前是一个独立的第三方开源项目（不属于 babel 官方）。它是为了让 ESLint 能够看懂 babel 转换出来的那些前言/实验性语法二存在的。
      + 历史任务: “全面降维” （都低策略的副作用，信誉发没法被 eslint 进行质量把关）。
        + 恐怖的 “时间差” : babel 与 ESLint 的更新速度严重脱节，当时前端信誉发的演进速度极快，从提案到正式写入 ECMAScript 标准需要经历 Stage 0 到 Stage 4 四个阶段。
        : babel 的策略: 因为历史原因 babel 的语法转换策略是，只要语法处于 Stage 1 或者 Stage 2（非常早起的草案） babel 就会立刻退出对应的转换插件，允许开发者在 ``webpack`` 中打包使用。
        : ESLint 的策略: 及其保守。 ESLint 团队严格遵守国际标准，只有当一个语法彻底进入 Stage 4 （正式成为国际标准）时， ESLint 核心包才会考虑去更新并支持。
        + 解析 “非 js 标准” 的魔改语法（升级 ESLint 也无解）: 有很多语法，根本就不是 ECMAScript 官方语法，无论你把 ESLint 升级到多少版本，它永远都不可能原生支持。
        : React 的 JSX ，早期 ESLint 原生根本看不懂 JSX 。
      + 如今现状: 不折腾了，直接升级 ESLint！
        + ESLint 变的更加前言: 现在的 ESLint 只要语法进入 Stage 3 就会提前同步适配，时间差会缩短到几个月甚至几天。
        + 默认标准的解放: 现在只要用现代版本 ESLint ，配置 ecmaVersions: "latest" 即可天然吃掉所有最新语法，完全不需要第三方 Parser 。
        + 生态的精简: Flow 已经退场， JSX 已经成为工业标准被 ESLint 默认支持。而像 TypeScript 这种非标准语法，大家已经同意改用专职的 @typescript-eslint/parser 。
      + 关系说明 eslint 与 babel-eslint 和 @babel/core 的关系（以 ?. 链式可选符为例）？
        : 持续升级问题: e.g. 有新的语法，@babel/core 需要升级新版本用来识别并转换新语法生成 AST 节点， babel-eslint 同样也要升级版本并识别 babel-core 转换的新的 AST 节点，并转换为 ESTree（eslint 语法校验时的抽象语法树）， ESLint 基本不用升级（当然如果不升级的话，ESLint 无法对新语法进行质量把关）。
          + 早期的时候， ESLint 直接通过自身的解析器（ Espree ）去直接读取源码中的 ?. 会直接崩掉，卡死到了源码转换 ESTree （ ESLint 校验规则的 AST 抽象语法树），后面所有的可以是别的源码都扫不到了，通过 ESLint 配置 parser 为 "babel-eslint" （ 新版本 "@babel/eslint-parser" ）后， ESLint 不在去读源码，把代码转换 ESTree 的事情让 babel-eslint 去干， babel-eslint 内部直接调用 @babel/core 的 @babel/parser 将源码解析为 AST 语法树，然后 babel-eslint 拿到这个 AST 语法树转换为 ESLint 能够识别的 ESTree 结构， ESLint 用校验规则去校验这个自己能够识别的 ESTree 结构（只是能识别的 ESTree 结构，至于是否真的能识别，取决于 ESLint 的版本，不识别就抛出一个 no-unused-expressions ，想要屏蔽报错就在 .eslintrc.js 加一个 { "no-unused-expressions": "off" } 。以 babel-eslint@10 为例转换``const a = obj?.prop`` 代码生成 ESTree 节点。
          >
            ```javascript
            // 省略
            {
              // 这是 babel-eslint 核心，桥接出来的链式可选专用节点
              "type": "OptionalMemberExpression",
              "optional": true,
              "object": {
                "type": "Identifier",
                "name": "obj",
                "loc": {
                  "start": { // obj 的起点
                    "line": 1,
                    "column": 10
                  },
                  "end": { // obj 的终点
                    "line": 1,
                    "column": 13
                  }
                }
              }
            }
            // 省略
```
          + 版本问题汇总
            + babel@6.x 时代无法识别 ?. 新语法（包括最后一个版本），可选链式符是在 @babel@7.x 时代纳入了 @babel/core 的语法识别范畴（主要是时间差，可选链式符进入提案的时，babel 已经演进了 babel7 了，babel6 不在维护了）。
            + eslint@^7.5.0 默认解析器 ESTree 原生支持 ?. 语法校验。




## 用途

+ 语法转换: 把箭头函数、解构赋值等新特性转换为旧版 js 语法。
: 对 babel 而言，“改变了代码骨架” 的才叫语法（e.g. 箭头函数）。“仅仅是多了一个全局工具函数” 的只能叫 API 特性（e.g. Promise ）。
  + 覆盖范围: 包括箭头函数、 const/let 、解构赋值（ Destructuring ）、可选链（ ?. ）、类（ Class ）、 async/await 等。这些特性的共同点是创造了老版本 js 引擎根本看不懂的全新符号、关键或结构。
  + 转换原则: 修改 AST （语法树物理重写）。
    + 解析（ Parse ）: babel 的解析器将新语法读取并切碎，生成包含新节点（e.g. ArrowFunctionExpression ）的 babel AST。
    + 转换（ Transform ）: babel 的核心插件介入。它会在内存中直接修改、重组这可语法树，把新节点抹去，用老语法（e.g. 普通的 FunctionExpression ）拼装出一个全新的老语法树。
    + 生成（ Generate ): 最后， babel 根据这棵树被修改后的老语法树，吐出符合旧引擎标准的字符串代码。
  + 官方配置体现: 在 babel 的配置中，这对应的是各种 plugins （插件），e.g. @babel/plugin-transform-arrow-functions 专门用来把箭头函数语法树重写为普通函数语法树。



+ Polyfill（ Built-ins ）补丁: 为就环境补充确实的全局对象和方法（e.g. Promise 、Array.from ，借助 core-js ）。
: 这些特性的共同点是没有发明任何新语法符号，它们知识 js 原生环境在全局对象（ window/global ）或原型链（ prototype ）上新增的函数或类。
  + 覆盖范围
    + 全新的全局对象: Promise 、 Map 、 Set 、 Proxy 、 Symbol 。
    + 全局对象上的新方法: Object.assign() 、 Array.from() 、 Number.isNaN() 。
    + 实例对象上的新方法: Array.prototype.includes() 、 String.prototype.padStart() 。
  + 转换原则: 注入补丁（运行时污染宿主环境修复），以 Promise 为例。
    + 不改洞源码结构: 保留 new Promise() 的写法不变。
    + 引入运行时补丁: 通过在打包后的代码顶部（或按需 babel6 晚期开始支持）注入一段兼容代码（通常由底层依赖 core-js 提供）。这段代码会在浏览器启动的第一时间执行，判断如果当前环境没有 window.Promise ，就用纯 ES5 的代码手动写一个伪造的 Promise 挂在到 window 上。
  + 官方配置体现: 在 babel 的配置中，这对应的是 Polyfill （垫片）或 @babel/runtime 机制。
    + Polyfill （垫片机制）: 直接改造世界/污染全局。
    : **代表配置:** @babel/preset-env 搭配  ``{ useBuiltIns: "usage" }`` （底层依赖 core-js ）。
    : **技术逻辑:** babel 会在监测你用到了 Promise 时，自动在文件顶部加入  ``import "core-js/modules/es.promsie.js"`` ，直接引入插件修改宿主环境，简易伪代码如下
    >
        ```javascript
        // 伪代码
        if (!window.Promise) {
          window.Promise = MyCustomPromiseImpl; // 强行把 Promise 挂在到全局
        }
        ```
    : **转换后的源码:** 源码写的是 new Promise() ， babel 转换后仍然是 new Promise() ，没有任何改变。只是在项目的入口处自动加了一句 ``import "core-js/modules/es.promsie.js"`` 。
    : 适用场景: 独立的应用，e.g. 开发一个后端台历系统，一个移动端 App 网页。开发者拥有对整个网页环境的绝对控制权，直接污染全局变量是最省事、新能最好的做法。




    + @babel/runtime 机制: 保持全局干净的局部沙箱。
    : **代表配置:** 安装 @babel/plugin-transform-runtime 插件。
    : **技术逻辑:** 绝对不碰、不修改全局的 window.Promise 。它通过直接篡改和重写你的代码逻辑，把所有用到 Promise 的地方替换为一个临时的、局部的私有变量。
    : **转换后的源码:** e.g. 源码为 ``const p = new Promise()`` ，转换后的代码如下
    >
```javascript
// 转换后的（ babel 编译出的代码）
var _promise = require('@babel/runtime-corejs3/core-js-stable/promise');
const p = new _promise(); // 原本的全局 Promise 消失了，变成了局部变量
```
    : **适用场景:** 第三方组件库 npm 包。e.g. 你正在开发一个类似于 axios 的开源库，发布给全世界的人使用。如果你的苦在别人的网页里强行修改了全局的 window.Promise ，可能会直接覆盖并搞崩别人网页里原本自定义的 Promise 逻辑。此时，用 @babel/runtime 把它所在哭的内部 “私下解决” ，是及其负责任的做法。
      + 混用翻车: 如果写一个库项目，在 .babelrc 的 presets 的 @babel/preset-env 既配置了 ``{ useBuiltIns： "usage" }`` ，又在 plugins 配置了 @babel/plugin-transform-runtime （具体是开启了配置项 corejs）， babel 就会陷入精神分裂，配置如下。
      : 
        ```javascript
        module.exports = {
          presets: [
            ["@babel/preset-env", {
              // 这里错误的设置为了 "usage"，库项目一般把 useBuiltIns 设置 false！交给 transform‑runtime 处理polyfill
              useBuiltIns: "usage",
            }]
          ],
          plugins: [
            [
              "@babel/plugin-transform-runtime",
              {
                corejs: 3, // 这里又开启了 API polyfill，使用 runtime‑corejs3 设置局部 API
                helpers: true, // 复用helper工具函数，避免重复生成代码，默认true
                regenerator: true // 处理 async/await generator
              }
            ]
          ]
        };
        ```
      : babel 先通过方案二 plugins 把代码中的 new Promise() 改为了 new _promise() 。
      : 然后根据方案一发现源码中的全局单词 Promise 已经找不到了，方案一就不在导入全局补丁。
      : 结果打包出来的代码体积又大、逻辑又混乱，完全失去了优化的意义。
      > 因此，需要根据自己是在写 “网站应用” 还是在发布 npm 组件库，在这两个方案里明确的进行 “二选一”，是前端构建工程中最基本的规范，配置了 @babel/plugin-transform-runtime 的 corejs 就要把 @babel/preset-env 的 useBuiltIns 设置为 false。




+ 插件化扩展: 支持 JSX 、 TypeScript 的转义。
  + TypeScript: 微软开发的开源编程语言，设计初衷是为了解决 javascript 在开发大型项目时 “代码难维护、容易写出 bug ” 的问题。
  : 通过 @babel/preset-typescript 支持 ts 的转换，工作方式非常粗暴且高效: 只做擦除，不做转换，更不做检查。
  : babel6+ 时代使用 ts-loader 不让 babel 见到 ts 代码（ @vue/cli-plugin-typscript 内部也是封装了 ts-loader ）。

  + JSX（JavaScript XML） : 是 javascript 的一种语法扩展，允许你在 javascript 代码里直接写 HTML 标签（React 和 Vue 等框架支持）。
    + 需要用到的包（这里没有列举 React 的 jsx 插件包）
      + babel-plugin-transform-vue-jsx （ vue2 环境，需要 babel6+ 环境，还需要安装其他插件 babel-plugin-jsx-event-modifiers 、 babel-helper-vue-jsx-merge-props 等配合使用。
      + @vue/babel-preset-jsx （ vue2 环境，是 preset 预设，需要 babel7+ 环境，由于历史原因 vue 官方将 4 个 plugin 整合为了 preset ）。
      + @vue/babel-preset-app （ vue2/3 环境，包含 ts 的支持，需要 babel7+ 环境）。
    + jsx 的支持包都是框架自己维护，未像 typescript 一样由 babel 统一维护的原因？
      : 虽然用 react 和 vue 写 jsx 的语法一样，但是 “底层目标” 完全不同。 babel 官方如果去写这些，就意味着 babel 团队必须深度精通，并实时同步维护 react 和 vue 的所有底层框架原理，这显示是现实的。
      + React （由 Meta 开发维护）: 把 jsx 变成 react 自己的虚拟 dom 对象。 babel 需要把它编译为 React.createElment 或 _jsxRuntime.jsx() 。
      + Vue （由尤雨溪团队开发维护）: Vue 的 jsx 插件必须把它编译为 vue 专属的 createVNode 或 h 函数，并且要在编译时自动分析出哪些是动态数据，打上标记，以便 vue 运行时进行高性能的 Diff 算法更新。
    + 两个框架的 “内部特性和指令” 天差地别， jsx 允许扩展很多特有的高级语法，二这些语法在不同的框架里有完全不同的行为规则。
      + vue 特有的指令（ Directives ）: vue 的核心特色是 v-model （双向绑定）、 v-show 、 v-loading 等。在 vue 的 jsx 里，你可能会写？？？
      + react 的事件与组件通信: react 没有指令，它完全靠原生的 props 回掉参数（e.g. onChange={handleChange} 。他的转义逻辑非常纯粹，不需要任何负责的指令逻辑转换。
