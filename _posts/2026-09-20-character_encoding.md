## 前言
常见的概念介绍。
+ 字节和比特: 1个字节 = 8个比特，比特是计算机最小的信息单元，只能存储 0 和 1。
+ `Unicode` 字符集（统一码、万国码）: 是一套全球统一的字符集，目标：给世界上几乎所有文字、符号分配唯一编号（解决了早年各国独立造字符集导致的一套编码只能覆盖一种语言的窘境）。
+ 码点: `Unicode` 给每一个字符分配唯一数字，这个数字就叫**码点（Code Point）**，写法 `U+16` 进制数。
+ 平面（码点分区）: 把全部码点，按照每 65536（0x10000）个码点划分为一个**平面**，一共 17 个平面：Plane0 ~ Plane16
  + 0号平面: U+0000 ~ U+FFFF。
  > + `U+D800 ~ U+DFFF` : **代理区（Surrogate Zone）**，专门给 **UTF-16 编码机制** 预留，**不能直接作为独立字符码点使用**。
  > + `U+E000 ~ U+F8FF`：**私有使用区 PUA（Private Use Area）**，留给应用自定义字符，**可以直接当成独立码点** 共 6400 个码点，自定义字体文件最常使用的就是 0号平面的自定义码区。
  > + 其它: 英文、标点、拉丁文、希腊文、常用中文（U+4E00~U+9FFF）、日文韩文。
  + 辅助平面: U+10000/U+100000 ~ U+1FFFF/U+10FFFF（1 ~ 16 号平面）。
  >  + 1 ~ 14号平面: 存放 emoji、古籍汉字、甲骨文、少数民族文字、古欧洲文字等。
  >  + 15 ~ 16号平面: 整片平面不分配官方字符，完全留给厂商 / 程序自定义字形。
+ utf-8: 针对 unicode 字符集的编码方案，1~4 字节动态编码，编码方案（码点转字节具体的实现）。
: | Unicode码点范围 | 码元大小 | 码元数量 | 二进制模板 | 可承载有效bit |
| ---- | ---- | ---- | --- | ---- |
| `U+0000 ~ U+007F` | 1 字节 | 1 | `0xxxxxxx` | 7 bit |
| `U+0080 ~ U+07FF` | 2 字节 | 2 | `110xxxxx 10xxxxxx` | 11 bit |
| `U+0800 ~ U+FFFF` | 3 字节 | 3 | `1110xxxx 10xxxxxx 10xxxxxx` | 16 bit |
| `U+10000 ~ U+10FFFF` | 4 字节 | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | 21 bit |

  > + 21个bit 刚好有效覆盖 17 号平面的最大bit数，码点 `U+10FFFF` 转二进制：`1 0000 1111 1111 1111 1111`，一共 **21 bit**。
  + **首字节1的数量决定总字节数；后续延续字节必须以 `10` 开头**，用来校验。

+ utf-16: 针对 unicode 字符集的编码方案，2/4 字节动态编码，编码方案（码点转字节具体的实现）。
: | 码点范围 | 编码方式 | 码元大小 | 码元数量 | 二进制模板 | 可承载有效bit |
| ---- | ---- | ---- | ---- | ---- | ---- |
| U+0000 ~ U+FFFF | 直接映射，码点值作为码元 | 2字节 | 1 | `xxxxxxxx xxxxxxxx` | 16bit |
| U+10000 ~ U+10FFFF | 高位代理 + 低位代理 | 4字节 | 2 | 高位代理： `0xD800~0xDBFF`<br />`110110xx xxxxxxxx`<br>低位代理：`0xDC00~0xDFFF`<br />`110111xx xxxxxxxx` | 20bit |

  > + 0号平面预留的 `utf-16` 代理区 `U+D800 ~ U+DFFF`，
  > + 代理对计算逻辑: 辅助平面最小码点 `U+10000` ， `val = codePoint - 0x10000` ， `val` 的 `bit` 数量范围为 1 ~ 20，代理对的可承载有效 bit 为 20 位，解码的时候再把 `U+10000` 加回去形成完整的 21 位码点。
  > + 高位代理运算: High = 0xD800 + (val >> 10)。
  > + 低位代理运算: Low = 0xDC00 + (val & 0x3FF)。

+ utf-32: 针对 unicode 字符集的编码方案，4 字节固定长度编码，编码方案（码点转字节具体的实现）。
: | 码点范围 | 编码方式 | 码元大小 | 码元数量 | 二进制模板 | 可承载有效bit |
| ---- | ---- | ---- | ---- | ---- | ---- |
| U+0000 ~ U+10FFFF | 码点直接作为32bit码元，高位补0 | 4字节 | 1 | `00000000 000000xx xxxxxxxx xxxxxxxx` | 仅使用低位 21bit |

+ 码元: 某种编码格式下，存储/传输时的最小单元。
: | 编码名称 | 单个码元大小 | 码元定义 | 码点与码元关系 | 特点 |
| ---- | ---- | ---- | ---- | ---- |
| UTF-8 | 8 bit（1字节） | 1字节为1个码元 | 1个码点 = 1~4 个码元 | 可变长度编码；ASCII字符单字节，兼容性好；互联网主流 |
| UTF-16 | 16 bit（2字节） | 2字节为1个码元 | 1个码点 = 1 或 2 个码元 | 可变长度编码；0号平面字符1个码元，辅助平面字符需要2个码元（代理对） |
| UTF-32 | 32 bit（4字节） | 4字节为1个码元 | 1个码点 = 1 个码元 | 定长编码；任何Unicode字符都只用1个码元，查找简单；占用空间大 |

  > js 源码文件可以保存为 utf-8，但 **内存字符串内部是UTF-16** 编码（也就是程序运行时声明的字符
  串），`str.length` 统计**UTF-16码元个数**。

+ 非字符 Noncharacter 码点: 存在两套清单。
  - 所有平面末尾 2 个码点（共 17 平面 ×2 =34 个），`U+nFFFE`、`U+nFFFF`，n 从 0 到 16。
  - BMP 中连续块 U+FDD0 ~ U+FDEF（16 个），之所以设置一段连续的、确定无效的码点，**给程序内部使用，用于标记、分隔、私有占位符**，永远不会分配字符。Unicode 标准明确规定: 任何外部交换的文本中，**不允许出现 U+FDD0~U+FDEF**，软件读到它们，应当当成无效数据处理。




## 大端序/小端序
大端序（Big-Endian）和小端序（Little-Endian）是计算机在内存中存储**<font color=red>多字节</font>**数据时的两种不同的字节排列顺序。以0号平面的汉子“中”为例，Unicode 码点 `U+4E2D` ，**只需要 1 个 UTF-16 码元，不需要代理对**，16 位码元的值就是 `0x4E2D`。
> + 大端序：高位在前低位在后，最终写入的字节序为  `4E` `2D`。
+ 小端序: 低位在前低位在后，最终写入的的字节序为  `2D` `4E`。

由于存在存储方式上有大小端序不同的方式，就引出了大小端的标记问题（BOM - Byte Order Mark 字节序标记），用来做 BOM 的码点固定是 `U+FEFF`（零宽不换行空格），如果文件是大端序，这个码元值就会以 `FE` `FF` 的字符序列写入文件开头，如果文件是小端序，这个写入的字符序列就是 `FF` `FE` ，程序通过前两个字符进行假设推定可以得出当前文件到底是大端序还是小端序。

| 头部字节 | BE计算结果 | LE计算结果 | 测试结论 |
| ---- | ---- | ---- | ---- |
| FE FF | 0xFEFF ✅ | 0xFFFE ❌ | UTF16BE |
| FF FE | 0xFFFE ❌ | 0xFEFF ✅ | UTF16LE |

> + 0xFFFE 计算结果失败是因为此码元值对应的是 Unicode 的非字符 Noncharacter 码点，非字符码点上面有介绍，不允许出现在存储和传输中。
+ U+FEFF 这个码点转换的码元值 `FE` `FF`  如果不在文件开头，在文件内容中仍然是一个合法字符。

接着再以辅助平面的汉字**"𠀀"**为例，按照 utf-16 编码展示如下:

| 阶段 | 数值 | 说明 |
| ---- | ---- | ---- |
| 原始Unicode码点 | U+20000 | 辅助平面汉字，超出BMP，需要2个UTF-16码元（代理对） |
| 减去基准值 | 0x20000 - 0x10000 = 0x10000 | UTF-16代理对计算固定基准 |
| 高位代理(High)码元 | 0xD840 | 第一个16位码元，**码元顺序必须放在前面** |
| 低位代理(Low)码元 | 0xDC00 | 第二个16位码元，**码元顺序必须放在后面** |
| UTF-16BE（大端）字节存储 | D8 40 DC 00 | 每个16bit码元：高字节在前<br/>0xD840 → D8 40<br/>0xDC00 → DC 00 |
| UTF-16LE（小端）字节存储 | 40 D8 00 DC | 每个16bit码元：低字节在前<br/>0xD840 → 40 D8<br/>0xDC00 → 00 DC |
| BOM（UTF16文件头部标记） | 大端序: FE FF D8 40 DC 00<br />小端序: FF FE 40 D8 00 DC | 标记字符处于所有文本字符之前 |

BOM 应用的常见场景。

| 场景 | 是否加BOM | 原因说明 |
| ---- | ---- | ---- |
| UTF-16LE / UTF-16BE 文本文件 | ✅ **建议必须加BOM** | UTF16码元是2字节，存在大小端；BOM告诉解码器字节序。无BOM时程序无法区分BE/LE，极易乱码 |
| UTF-8 网页、JSON、JS、Shell脚本、Python源码 | ❌ **不能加BOM** | UTF8无字节序；BOM会变成隐藏U+FEFF字符，导致脚本报错、JSON解析失败、前端异常 |
| UTF-8 文本，专门给旧版Windows记事本（Win7）打开 | ✅ 可以加BOM | Win7记事本没有编码自动探测，带BOM可以让记事本识别为UTF-8，避免中文乱码 |
| UTF-8 跨平台通用文档（Linux/macOS读取） | ❌ 不加BOM | Linux生态惯例是无BOMUTF8，BOM会被当成一个真实空白字符 |
| UTF-32 文件 | ✅ 建议加BOM | UTF32有大小端，依靠BOM识别字节序，原理同UTF16 |

**win7 记事本的保存格式和编码对应关系**

| 编码选项(Win7记事本) | 底层编码 | 码元大小 | 是否存在大小端 | 文件头部BOM | BOM作用 | 汉字`中`磁盘字节（含BOM） |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| UTF-8 | UTF-8 | 1字节(8bit) | ❌ 无大小端 | EF BB BF（3字节） | 标记文件编码，**不标记字节序** | EF BB BF E4 B8 AD |
| Unicode | UTF-16LE（小端） | 2字节(16bit) | ✅ 小端 | FF FE（2字节） | 标记：后续码元是小端序 | FF FE 2D 4E |
| Unicode big endian | UTF-16BE（大端） | 2字节(16bit) | ✅ 大端 | FE FF（2字节） | 标记：后续码元是大端序 | FE FF 4E 2D |

> + `utf-8` 码元是单字节，不涉及多字节逻辑，所以不涉及大小端序存储问题。但是 Windows 的记事本（notepad.exe）保存为「UTF-8」时，**额外在文件最前面写入 3 个字节 `EF BB BF`，这个就是 UTF8-BOM**，这是 Windows 软件的行为，**不是 UTF-8 编码规范强制要求**，`EF BB BF` 就是把 BOM 字符 `U+FEFF` 用 UTF-8 编码出来的结果。
+ win7 系统的记事本只要保存选择 utf-8 ，就会强制写入 EF BB BF，不能直接保存为无 BOM 的 utf-8，到了 win10 以及 win11 后，选择 utf-8 就可以选择是否带 BOM 了。其次这个 utf-8 添加 BOM 仅仅是记事本软件的保存行为，其它，e.g. vscode、notepad++ 不会给 utf-8 文件设置 BOM。
+ win7 系统的记事本的 ANSI 编码不是固定编码，是系统区域设置对应的代码页 CP_ACP，对于简体中文系统而言 CP_ACP（代码页）为 936，底层是 GBK 编码（向下兼容 GB2312），注: GB18030 是 GBK 的超集；但简体中文 Win7 默认 CP936 是 GBK，不是 GB18030，查看命令 `chcp` 。

## javascript 中字符串定义
`Javascript` 中 `String` 类型是由零或者多个 `utf-16` 码元序列构成的字符序列，字符串的长度就是码元的数量。

| 写法 | 位数要求 | 码点范围 | 支持辅助平面 | ES版本 |
|---|---|---|---|---|
| `\xHH` | 固定2位 | U+0000 ~ U+00FF | ❌ | 早期JS |
| `\uHHHH` | 固定4位 | U+0000 ~ U+FFFF | ❌（只能手动代理对） | ES5 |
| `\u{...}` | 1~6位 | U+0000 ~ U+10FFFF | ✅ | ES6+ |

> 只能手动代理对: 以生僻字 "𠅤"（xí 多用于人名） `U+20164` 为例，`\u{20164}` -> `\uD840\uDD64`。
